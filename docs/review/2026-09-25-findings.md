# Findings, 2026-09-25: ticket sizing, a fast lane, antivirus on Windows

Findings only — nothing here is built. Each ends with a proposal and a question for the owner.
Evidence: five `/build` runs from a logged test run (same project; the plugin version and the model differ
between them, so they are indicative, not a controlled test).

## 1. Ticket sizing

**What the logs show.** Each build split at its first and last edit to product code (wall minutes):

| Build | Total | Before first code edit | Coding span (incl. review fixes) | After last code edit | Size |
|---|---|---|---|---|---|
| A | 26.2 | 10.7 | 5.0 | 10.5 | 3 files, 5 edits |
| B | 48.5 | 4.0 | 40.5 | 4.0 | 12 files, 56 edits |
| C | 65.7 | 5.6 | 52.9 | 7.2 | 13 files, 93 edits |
| D | 77.7 | 8.7 | 51.9 | 17.1 | 19 files, 74 edits |
| E | 88.8 | 4.4 | 45.9 | 38.5 | 12 files, 49 edits |

- **Every build pays a fixed cost of roughly 10–25 minutes** — reading in, the gate, the feature doc, the commit,
  the board — whatever its size. Build A spent 21 of its 26 minutes on it for 5 minutes of coding. (Build E's
  38.5 minutes "after" include a full suite slowed by antivirus and a failure caused outside the build; see §3.)
- The "coding span" includes review rounds and their fixes, so the true fixed cost is somewhat higher than the
  before + after columns. Measuring it exactly needs the reviews timed on their own — not done yet.

**For one person:** total time ≈ number of tickets × fixed cost + the coding itself. A 19-ticket milestone pays
the fixed cost 19 times: at ~15 minutes that is ~4¾ hours spent on overhead. Merging the smallest tickets saves
that overhead, but a ticket that grows too large costs more than it saves: a run's cost is steps × context, so a
build twice as long costs more than twice as much, and a larger diff makes each review round less sharp.
**The measured sweet spot is where builds B–D sit: 12–19 files, 40–55 minutes of coding.** Build A is below it.

**For a team:** size is not what blocks people. The plan's own Day-1 table says one lane has "9 tickets in a
strict chain": each waits for the one before it to merge, so that lane is one person's critical path however
small its tickets are. What lets several people work at once is **fewer waits**: `/tickets` already has *builds
against* (start from a stub of a frozen contract) — used on 2 of the 9 cross-lane links in that plan.

**Proposal (for your decision):**
1. `/tickets` merges a ticket into its lane neighbour when it touches **fewer than 4 files**, and splits one
   above **20 files** — numbers from the table above, re-measured after the speed fixes land.
2. `/tickets` prints each lane's **critical path** (the longest wait chain) and, for any chain longer than 3,
   proposes *builds against* a stub where the contract is frozen.
3. Keep cutting the fixed cost itself: the speed fixes already built (full suite 7 → 3 runs on one build) and
   STATUS.md (one command instead of 5–30 searches) both come off every ticket.

*Quality risk:* merging tickets makes one review cover more code. Mitigation: the rule caps at 20 files, and the
review rounds stay as they are. *Proof:* a milestone planned both ways, same verdicts, time and cost compared.

## 2. A fast lane for small projects

Today every product walks up to 17 phases. For a weekend tool or an internal script, several of them cost more
than they return — validating a market, a design system for one screen, a GitHub board for one person.

**Proposal (for your decision):** a lane the user chooses once, at `/vision`, recorded in `#Project policy`
(`lane: fast`) and shown by `status.py next` on every run — never the default, never chosen for the user.
- **Kept, unchanged:** vision (short form), scope with its out-of-scope list, architect, the security DoD in
  every build, the review round, the live-path check, the honest close. These are where the quality comes from.
- **Skipped, recorded as overrides** (`status.py set <phase> overridden`, reason "fast lane"): validate, eval
  (unless the product uses AI), deploy (unless it must be reachable).
- **Merged:** plan into scope (one milestone); structure and foundation in one sitting (batch mode already
  allows it); tickets as `TICKETS.md` only, no GitHub board; dev-check and test in one sitting.
- **Leaving the lane:** any time, by running a skipped phase — its override closes like any other.

*Quality risk:* by design it does less, so it must stay visible: STATUS.md shows every override, and the close
names the lane. It must never change a verdict *inside* a phase it runs. *Proof:* the Step 4 small product run
both ways; the phases the fast lane keeps must give the same verdicts.

**Question:** is the fast lane wanted for the Step 4 comparison, or after it?

## 3. Antivirus on Windows (for `/foundation`)

**Measured on the logged test run** (741 tests): full suite **313 s** with Norton scanning, **131 s** with the
project folder and the package caches (`uv`, `pnpm`) excluded, **111 s** with Norton off. The exclusions give
back ~2.4× on every test run, and a build runs the full suite 2–3 times.

**Proposal:** `/foundation`, on Windows only, after the first full test run, **tells** the user (never does it):
- what to exclude: the project folder, and the package caches the stack uses (`%LOCALAPPDATA%\uv`,
  `%LOCALAPPDATA%\pnpm`, `%LOCALAPPDATA%\npm-cache`, `%LOCALAPPDATA%\pip\Cache`);
- how: for Microsoft Defender, `Add-MpPreference -ExclusionPath "<folder>"` in an administrator PowerShell;
  for other antivirus, its own settings page;
- the trade-off in plain words: files in those folders are no longer scanned as they are written;
- the measurement: time the suite before and after, and record both in `docs/runbook.md`.

*Quality risk:* none to verdicts — a security setting is the user's call, so the skill only explains it.
*Proof:* a `/foundation` run on Windows shows the advice, and the runbook records both timings.
